第 5 章解决「报了什么错」，这一章回答「为什么和我想的不一样」——用任何三方中转站（API 网关）前值得先读一遍。具体报错排查见[第 5 章](../05-faq/)。

## 额度与倍率

- **额度是什么**：站点内的统一计费单位，默认按美元折算（如余额 `10` ≈ 可消耗 10 美元等值的 token）。它不是人民币余额，也不是 token 数。
- **价格怎么算**：`输入 token × 输入单价 + 输出 token × 输出单价`，再乘以密钥所属**分组倍率**与**模型倍率**。单价以控制台「模型广场 / 模型定价」页为准。
- **为什么和官方价格不同**：中转站按渠道采购，各站倍率策略不同；同一模型在不同分组下价格也可能不同。下单前先看定价页，不要按官方价估算。
- **定价页没有的模型**：说明未开放或未配置价格，调用会报错，先确认它出现在 [`/v1/models`](../03-api/#查询可用模型) 列表里。

## 扣费比预期多？

按顺序自查：

1. **输入也计费**：长上下文（贴入大文件、整段代码）的费用主要在输入侧，不是只有回答收费；
2. **流式中断照扣**：回复已开始生成后取消/断线，已生成的部分照常计费；
3. **预扣费机制**：部分任务开始前会按 `max_tokens` 预扣，结束后退回多扣部分——期间余额会被临时占用；
4. **多轮对话累积**：客户端每轮都会把历史消息重发一遍，上下文越长单轮越贵；
5. 对账以控制台 **使用日志** 为准（含每次调用的 token 数与费用），见[第 4 章](../04-quota-usage/)。

## 模型和官方不完全一样？

- **模型名以站点为准**：站内名称可能与官方有出入（映射、别名或带后缀），一切以 `/v1/models` 返回为准；
- **上下文/输出上限可能不同**：网关按渠道能力转发，个别模型的实际可用上下文与官方标称有差异；
- **同名不同渠道**：同一模型名背后可能由不同上游承接，风格与稳定性会有波动；对结果敏感的任务固定使用同一模型名并观察日志中的渠道信息。

## 响应慢、超时、429

| 现象 | 常见原因 | 处理 |
| --- | --- | --- |
| 首字等待久 | 上游渠道繁忙、高峰排队 | 稍后重试；看使用日志的耗时分布 |
| 中途断流 | 客户端超时设置过短、本地网络抖动 | 调大客户端 timeout；长回复务必开流式 |
| 429 Too Many Requests | 上游限流或站点并发限制 | 降低并发/重试间隔，指数退避重试 |
| 间歇性失败 | 某条渠道不稳定，命中时才失败 | 重试一次往往就好；持续失败联系管理员 |

## 稳定性说明

- 中转链路比官方直连多一跳，可用性 = 站点可用性 × 上游可用性，对延迟敏感的场景要有心理预期；
- 密钥开启 **跨分组重试**（见[第 1 章](../01-api-key/)）后，本分组无可用渠道时会自动尝试其他分组，成功率更高但计费倍率可能不同；
- 关键业务建议：客户端侧实现重试 + 超时兜底，重要数据不要依赖单次调用成功。

## 数据与隐私

- **对话内容对站点可见**：网关转发的是明文请求。不要通过中转站发送密码、密钥、客户数据等敏感信息；
- 不要把 `sk-` 密钥提交进代码仓库或打包进客户端分发——它等同于账户余额的钥匙；
- 定期在「使用日志」核对异常调用（见[第 5 章](../05-faq/#密钥疑似泄露怎么办)的泄露处理流程）。

## 与官方 API 的兼容性

- 本站提供的是 **OpenAI 兼容层**：`chat/completions`、`embeddings`、`messages` 等主流端点行为对齐，但不承诺 100% 覆盖官方全部参数与行为（个别高级参数可能被忽略）；
- 各端点的实际可用性取决于已配置的渠道，以 `/v1/models` 和实际调用为准（见[第 3 章](../03-api/)）；
- 从官方 SDK 迁移只需改 `base_url` 和密钥两处，其余代码不用动（见[第 2 章](../02-clients/)）。
